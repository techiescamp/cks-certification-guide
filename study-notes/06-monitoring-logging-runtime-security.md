# Domain 6: Monitoring, Logging and Runtime Security (20%)

> **Exam Weight: 20%**: This domain tests whether you can detect suspicious behaviour while workloads run, trace it back to a pod, stop it, keep containers immutable, and record who did what through the Kubernetes audit log.

The earlier domains try to stop attacks before they start. This domain assumes something got through. So you need two kinds of evidence. Falco watches system calls on each node and raises alerts when a process does something unusual, such as opening `/dev/mem` or starting a shell. The Kubernetes audit log records every request to the API server, so you can see which user or ServiceAccount changed what. Then you use node tools such as `crictl`, `journalctl` and `ps` to connect an alert to a pod and act on it.

## 1. How Falco Works

Falco is a runtime security tool. It runs on each node and reads system calls from the kernel through a driver. The default `falco.yaml` selects the modern eBPF driver (`engine.kind: modern_ebpf`). Falco checks each event against its rules. When a rule's condition matches, Falco writes an alert with the rule's output text.

A rule has a condition written with Falco fields. The fields you will use most often are these:

| Field | Meaning |
|-------|---------|
| `evt.type` | The system call, such as `openat` or `execve` |
| `evt.time` | The time of the event |
| `proc.name` / `proc.cmdline` | The process name, and the name plus its arguments |
| `user.name` | The user that ran the process |
| `fd.name` | The file path (or the connection for sockets) |
| `container.id` | The first 12 characters of the container ID, or `host` for host processes |
| `container.name` / `container.image.repository` | The container name and image |
| `k8s.pod.name` / `k8s.ns.name` | The pod name and namespace |

The `container.*` and `k8s.*` fields come from the container runtime, so Falco can tell you which pod caused an alert. To list every field that your Falco version supports, run `falco --list`.

This approach is called behavioural analytics. Falco does not look at images or manifests. It watches what processes actually do, so it catches attacks that static scanning misses.

## 2. Falco Rules Files and Load Order

When Falco is installed from the packages, its files live under `/etc/falco`.

| Path | Purpose |
|------|---------|
| `/etc/falco/falco.yaml` | Main configuration: outputs, driver, rules files |
| `/etc/falco/falco_rules.yaml` | The default rules. Do not edit this file, because upgrades replace it |
| `/etc/falco/falco_rules.local.yaml` | Your custom rules and overrides |
| `/etc/falco/rules.d/` | A directory for more rules files |

The order is set by `rules_files` in `falco.yaml`. Its default looks like this:

```yaml
rules_files:
  - /etc/falco/falco_rules.yaml
  - /etc/falco/falco_rules.local.yaml
  - /etc/falco/rules.d
```

Falco loads these from top to bottom. This order matters, because an override only works if it loads after the rule it changes. So the default rules load first, then your local file, then the files in `rules.d`.

To see which rules are loaded, or the details of one rule, use these commands.

```bash
falco -L
falco -l "Terminal shell in container"
```

## 3. Writing, Overriding and Appending Falco Rules

### A custom rule

A rule needs `rule`, `desc`, `condition`, `output` and `priority`. This rule fires when a process in a container opens a sensitive device file such as `/dev/mem`. It uses a list for the paths and the `container` macro, which the default rules file already defines. Put it in `/etc/falco/falco_rules.local.yaml`.

```yaml
- list: sensitive_dev_files
  items: [/dev/mem, /dev/kmem, /dev/port]

- rule: Container opened sensitive device file
  desc: A process in a container opened a sensitive device file under /dev
  condition: >
    evt.type in (open, openat, openat2)
    and container
    and fd.name in (sensitive_dev_files)
  output: >
    Sensitive device opened (file=%fd.name proc=%proc.name cmd=%proc.cmdline
    user=%user.name container_id=%container.id container_name=%container.name
    image=%container.image.repository pod=%k8s.pod.name ns=%k8s.ns.name)
  priority: WARNING
  tags: [container, filesystem]
```

### Overriding an existing rule

To change a default rule, do not copy the whole rule and do not edit `falco_rules.yaml`. Instead, add an entry with the same name to your local file, list only the keys you change, and add an `override` block. The `override` block says, for each key, whether to `append` to the existing value or `replace` it.

- For rules, you can append to `condition`, `output`, `desc`, `tags` and `exceptions`.
- For rules, you can replace `condition`, `output`, `desc`, `priority`, `tags`, `exceptions`, `enabled` and a few more.
- For macros, you can append to or replace `condition`. For lists, you can append to or replace `items`.
- You cannot use `append` and `replace` on the same key.

This override changes the output of the default `Terminal shell in container` rule to a given format and raises its priority. The original condition stays as it is.

```yaml
- rule: Terminal shell in container
  output: Shell in container (time=%evt.time user=%user.name container_id=%container.id container_name=%container.name pod=%k8s.pod.name ns=%k8s.ns.name cmd=%proc.cmdline)
  priority: WARNING
  override:
    output: replace
    priority: replace
```

This override appends an extra check to the condition of the same rule, so shells in an approved debug image no longer alert. Note that the appended text starts with `and`, because Falco joins it to the end of the existing condition.

```yaml
- rule: Terminal shell in container
  condition: and not container.image.repository = "registry.example.com/debug-tools"
  override:
    condition: append
```

To add items to an existing list, append to `items`.

```yaml
- list: sensitive_dev_files
  items: [/dev/nvram]
  override:
    items: append
```

To turn a rule off, replace `enabled`.

```yaml
- rule: Terminal shell in container
  enabled: false
  override:
    enabled: replace
```

> [!NOTE]
> Older guides use `append: true` on a rule, macro or list. That key still works, but it is deprecated and will be removed in Falco 1.0.0. Use the `override` block instead.

### Verify

Check that the configuration and all rules files load without errors before you restart the service. `--dry-run` loads everything but processes no events.

```bash
falco --dry-run
falco -l "Terminal shell in container"
```

### Common mistakes

- Putting the override in a file that loads before `falco_rules.yaml`. It then fails, because the rule does not exist yet.
- Forgetting the leading `and` or `or` when you append to a condition.
- Misspelling the rule name. The name must match the default rule exactly, including capital letters.
- Editing `falco_rules.yaml` directly. It works until the next upgrade, and it is not what tasks usually ask for.

## 4. Running Falco and Reading Alerts

The packages install one systemd unit per driver, such as `falco-modern-bpf.service`, `falco-kmod.service` or `falco-custom.service`. Enabling one of them also creates the alias `falco.service`. So first find out which unit is running.

```bash
systemctl list-units | grep falco
systemctl status falco
```

After you change rules or `falco.yaml`, restart Falco. Falco also watches its config and rules files and reloads on changes (`watch_config_files: true`), but a restart makes the change certain.

```bash
systemctl restart falco
systemctl status falco
```

### Where the alerts go

In the default `falco.yaml`, alerts go to standard output and to syslog, and file output is off.

```yaml
stdout_output:
  enabled: true
syslog_output:
  enabled: true
file_output:
  enabled: false
  keep_alive: false
  filename: ./events.txt
```

Because the service sends standard output to the journal, you can read alerts with `journalctl`. Use the real unit name you found above.

```bash
journalctl -u falco-modern-bpf.service -f
journalctl -u falco-modern-bpf.service --since "15 min ago" | grep "Sensitive device"
```

On Ubuntu nodes, syslog also writes the alerts to `/var/log/syslog`.

```bash
grep falco /var/log/syslog | tail -20
```

If a task asks you to save alerts to a file, enable `file_output` in `/etc/falco/falco.yaml` with an absolute path, then restart Falco.

```yaml
file_output:
  enabled: true
  keep_alive: false
  filename: /var/log/falco/events.txt
```

Use `json_output: true` if the task wants alerts in JSON format.

### Verify

Trigger a rule on purpose and watch it appear. `kubectl exec` with `-it` starts a shell with a terminal, which fires the `Terminal shell in container` rule.

```bash
kubectl run falco-test --image=nginx:1.27
kubectl exec -it falco-test -- sh -c 'exit'
journalctl -u falco-modern-bpf.service --since "2 min ago" | grep -i shell
```

### Common mistakes

- Running `journalctl -u falco` when the journal stores the entries under the real unit name. If you see no entries, use the name from `systemctl list-units`.
- Writing the file output to a directory that does not exist.
- Expecting `kubectl exec` without `-t` to fire the shell rule. That rule needs a terminal (`proc.tty != 0`).

## 5. Worked Example: Find the Pod That Touches /dev/mem

A realistic task looks like this. Several Deployments run in the cluster. One of their pods reads `/dev/mem`. Use Falco to find which one, then scale that Deployment to 0 replicas.

**Step 1: Make sure a rule catches the behaviour.** If no default rule covers it, add the custom rule from section 3 to `/etc/falco/falco_rules.local.yaml` and restart Falco. Do this on the node where the pods run, because Falco only sees the system calls of its own node.

```bash
kubectl get pods -A -o wide
ssh node01
sudo -i
vim /etc/falco/falco_rules.local.yaml
falco --dry-run
systemctl restart falco
```

**Step 2: Read the alerts.** Wait a minute for the pod to repeat the behaviour, then read the alert lines.

```bash
journalctl -u falco-modern-bpf.service --since "5 min ago" | grep "Sensitive device"
```

An alert line contains the container ID, for example `container_id=4f1c2a9e7b3d`. It may also contain the pod name. If `pod=` is empty or `<NA>`, map the container ID yourself in the next step.

**Step 3: Map the container ID to a pod.** `crictl ps` shows the pod name in the `POD` column. `crictl inspect` also shows the Kubernetes labels of the container, which include the pod name and namespace.

```bash
crictl ps | grep 4f1c2a9e7b3d
crictl inspect 4f1c2a9e7b3d | grep -E 'io.kubernetes.pod.(name|namespace)'
```

**Step 4: Find the Deployment that owns the pod.** A Deployment pod is owned by a ReplicaSet, and that ReplicaSet is owned by the Deployment.

```bash
kubectl -n team-b get pod mem-reader-6d5f8b7c9-x2kqp -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'
kubectl -n team-b get rs mem-reader-6d5f8b7c9 -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'
```

**Step 5: Scale it to 0.** This stops the pods but keeps the Deployment, so others can still investigate it.

```bash
kubectl -n team-b scale deployment mem-reader --replicas=0
```

### Verify

The Deployment should show `0/0` ready, and new alerts for that container should stop.

```bash
kubectl -n team-b get deploy mem-reader
journalctl -u falco-modern-bpf.service --since "1 min ago" | grep "Sensitive device"
```

### Common mistakes

- Looking at Falco on the control plane node when the pod runs on a worker node.
- Deleting the pod instead of scaling the Deployment. The ReplicaSet just creates a new pod.
- Deleting the Deployment when the task only asks you to scale it down.

## 6. Investigating an Attack on a Node

An attack moves through phases. Knowing them helps you decide what to look for and in which log.

| Phase | What it looks like | Where you see it |
|-------|-------------------|------------------|
| Initial access | A shell or unexpected process starts in a container | Falco shell rules, `crictl ps`, `ps` |
| Execution | A dropped binary or script runs | Falco `execve` events, `/proc/<pid>/exe` |
| Privilege escalation | Access to `/dev/mem`, kernel modules, setuid binaries | Falco alerts, privileged pods in the API |
| Credential access | Reads of `/etc/shadow`, ServiceAccount tokens, Secrets | Falco sensitive file rules, audit log `secrets` events |
| Discovery and lateral movement | Calls to the API server, scans of other pods | Audit log, Falco network rules |
| Persistence | New RBAC bindings, new DaemonSets, changed static pods | Audit log `create` and `update` events |
| Impact and exfiltration | Outbound connections, deleted data, cryptominers | Falco alerts, `ss`, high CPU in `crictl stats` |

### Node commands that answer most questions

Use `crictl` to list containers and pods on the node, including stopped ones.

```bash
crictl ps -a
crictl pods
crictl inspect <container-id>
crictl logs <container-id>
crictl stats
```

Use `ps` to see processes, and `/proc` to see what binary a process runs and how it was started.

```bash
ps -ef --forest
ps aux --sort=-%cpu | head
ls -l /proc/<pid>/exe
cat /proc/<pid>/cmdline | tr '\0' ' '
cat /proc/<pid>/cgroup
```

The cgroup path of a container process contains its container ID. So it links a suspicious host PID back to `crictl ps`.

Use `ss` to see which processes listen on ports or hold connections.

```bash
ss -tlnp
ss -tnp
```

Use `journalctl` to read service logs, such as the kubelet, the container runtime and Falco.

```bash
journalctl -u kubelet --since "30 min ago"
journalctl -u containerd --since "30 min ago"
```

### Verify

You should be able to connect every alert to a node, a container ID, a pod, a namespace and an owner (Deployment, DaemonSet or user). Write these down before you act, because scaling or deleting removes the evidence.

### Common mistakes

- Killing a process on the node instead of fixing the workload. The kubelet restarts the container and the problem comes back.
- Forgetting `-a` on `crictl ps`, so containers that already exited are hidden.

## 7. Immutable Containers at Runtime

An immutable container cannot change its own files while it runs. So an attacker cannot drop a tool, edit a config or replace a binary. You get there with three things:

1. **A read-only root file system** with `readOnlyRootFilesystem: true`.
2. **Writable `emptyDir` volumes** only for paths that the app really writes to, such as caches and PID files.
3. **An image without shells or package managers**, such as a distroless image, so there is nothing to run even if someone gets in.

This pod runs nginx with a read-only root file system. nginx writes to its cache directory and writes its PID file under `/var/run`, so both get an `emptyDir`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: immutable-nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    securityContext:
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
    volumeMounts:
    - name: cache
      mountPath: /var/cache/nginx
    - name: run
      mountPath: /var/run
  volumes:
  - name: cache
    emptyDir: {}
  - name: run
    emptyDir: {}
```

To find pods that are not immutable yet, list the setting for every container.

```bash
kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,READONLY:.spec.containers[*].securityContext.readOnlyRootFilesystem,PRIVILEGED:.spec.containers[*].securityContext.privileged'
```

A container without a shell is hard to debug. Instead of adding a shell back to the image, attach a temporary debug container that shares the process namespace of the target container.

```bash
kubectl debug -it immutable-nginx --image=busybox:1.37 --target=nginx
```

### Verify

A write to the root file system should fail, and a write to the `emptyDir` should work.

```bash
kubectl exec immutable-nginx -- touch /etc/test
kubectl exec immutable-nginx -- touch /var/cache/nginx/test
```

The first command fails with `Read-only file system`.

### Common mistakes

- Setting `readOnlyRootFilesystem` at the pod level. It is a container-level field.
- Not adding an `emptyDir` for the paths the app writes to, so the container goes into `CrashLoopBackOff`. Check `kubectl logs` to see which path failed.
- Leaving `privileged: true` on the container. A privileged container can remount the file system and undo the protection.

## 8. Kubernetes Audit Logging

The API server can record every request in an audit log. Each event says who made the request, what they did, to which resource and when. Audit logging is off until you give the API server a policy file and a log backend.

### Audit levels and rule order

Each rule in the policy sets a level:

| Level | What is logged |
|-------|----------------|
| `None` | Nothing for requests that match |
| `Metadata` | User, timestamp, resource, verb and so on, but no request or response body |
| `Request` | Metadata and the request body |
| `RequestResponse` | Metadata, the request body and the response body |

The API server checks the rules from top to bottom, and **the first rule that matches decides the level**. So put the specific rules first and a catch-all rule last. If a broad rule comes first, the specific rules below it never apply.

Requests pass through stages: `RequestReceived`, `ResponseStarted` (only for long-running requests such as `watch`), `ResponseComplete` and `Panic`. Most policies skip `RequestReceived` with `omitStages`, because it only duplicates the later event.

### An example policy

This policy follows a typical set of instructions. Secrets are logged at `Metadata`, because `Request` would write the secret data into the log. Pod and Deployment changes in `prod` are logged in full. Noisy watch requests from kube-proxy are dropped. Everything else is logged at `Metadata`. Save it as `/etc/kubernetes/audit/policy.yaml`.

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - "RequestReceived"
rules:
  - level: None
    users: ["system:kube-proxy"]
    verbs: ["watch"]
    resources:
    - group: ""
      resources: ["endpoints", "services"]
  - level: Metadata
    resources:
    - group: ""
      resources: ["secrets", "configmaps"]
  - level: RequestResponse
    namespaces: ["prod"]
    verbs: ["create", "update", "patch", "delete"]
    resources:
    - group: ""
      resources: ["pods"]
    - group: "apps"
      resources: ["deployments"]
  - level: Metadata
```

### The kube-apiserver flags

Add these flags to `/etc/kubernetes/manifests/kube-apiserver.yaml`. `--audit-log-path` turns on the log backend. Without it, the API server writes no audit file. The other three flags control rotation: days to keep, number of old files to keep, and the size in megabytes before rotation.

```yaml
- --audit-policy-file=/etc/kubernetes/audit/policy.yaml
- --audit-log-path=/var/log/kubernetes/audit/audit.log
- --audit-log-maxage=30
- --audit-log-maxbackup=10
- --audit-log-maxsize=100
```

### The volume mounts

The API server container must see both the policy file and the log directory. The policy is mounted read-only. The log directory must be writable. Add the mounts under the container's `volumeMounts` and the volumes under `spec.volumes`.

```yaml
volumeMounts:
- name: audit-policy
  mountPath: /etc/kubernetes/audit/policy.yaml
  readOnly: true
- name: audit-log
  mountPath: /var/log/kubernetes/audit/
  readOnly: false
volumes:
- name: audit-policy
  hostPath:
    path: /etc/kubernetes/audit/policy.yaml
    type: File
- name: audit-log
  hostPath:
    path: /var/log/kubernetes/audit/
    type: DirectoryOrCreate
```

As with any static pod change, the kubelet restarts the API server. If it does not come back, use `crictl ps -a`, `crictl logs` and `journalctl -u kubelet` as shown in Domain 5, section 7.

### Verify

Wait until the API server answers again, make a request that the policy covers, then look for it in the log. Each line is one JSON event.

```bash
kubectl get nodes
kubectl -n prod create secret generic audit-test --from-literal=key=value
tail -f /var/log/kubernetes/audit/audit.log
grep '"resource":"secrets"' /var/log/kubernetes/audit/audit.log | grep audit-test | tail -1
```

The fields you read most often are `user.username`, `verb`, `objectRef.resource`, `objectRef.namespace`, `objectRef.name`, `level`, `sourceIPs` and `responseStatus.code`. If `jq` is installed, it makes the events easier to read.

```bash
jq -c 'select(.objectRef.resource=="secrets") | {user: .user.username, verb, ns: .objectRef.namespace, name: .objectRef.name, level}' /var/log/kubernetes/audit/audit.log | tail
```

### Common mistakes

- Putting the catch-all rule first. The first match wins, so every request ends up at that level.
- Logging Secrets at `Request` or `RequestResponse`, which writes secret values into a plain text log.
- Mounting the policy file but not the log directory, or mounting the log directory read-only. The API server then fails to start.
- Pointing `--audit-policy-file` at a path that differs from the `mountPath`. The flag uses the path inside the container.

## 9. Hands-on Checklist

Before you move on, make sure you can do each of these tasks on a real cluster:

- [ ] Can you name the Falco rules files under `/etc/falco` and explain the order in which they load?
- [ ] Can you write a custom Falco rule that detects access to `/dev/mem` from a container?
- [ ] Can you override the output and priority of a default Falco rule with an `override` block in `falco_rules.local.yaml`?
- [ ] Can you append a condition to a rule and items to a list without copying the whole rule?
- [ ] Can you validate the rules with `falco --dry-run`, restart Falco and read its alerts with `journalctl`?
- [ ] Can you send Falco alerts to a file at a given path?
- [ ] Can you map a container ID from a Falco alert to its pod with `crictl`, then find and scale the owning Deployment to 0?
- [ ] Can you use `ps`, `/proc`, `ss` and `journalctl` to link a suspicious host process back to a container?
- [ ] Can you make a container immutable with `readOnlyRootFilesystem` and `emptyDir` volumes, and prove that writes fail?
- [ ] Can you debug a container without a shell using `kubectl debug --target`?
- [ ] Can you write an audit policy where the rule order gives each resource the right level?
- [ ] Can you add the audit flags and volume mounts to the kube-apiserver manifest and confirm that events reach the log?
- [ ] Can you find who created or deleted a given resource by searching the audit log?
